# Red team log

Scope: every attack in `docs/spec/APEX_MASTER_SPEC_V4.1.md` section 14 ("Red team"), checked against the code and
the unit tests in the repository.

**Environment and method.** This is a read-and-record pass. No device or emulator was run, no Gradle task was run
by this pass, and no code was changed. "Test covering it" names a test only when it was found by reading the test
sources; a test that exists is not claimed to be green (CI runs them). Attacks that need a device (Keystore, Doze,
OEM battery policy, TalkBack, 200 % font, RTL layout) can only be judged from code here.

**Result key.** Handled: the code path exists and a test pins it. Partly: the code path exists but a test is
missing, or a variant is not covered. Not handled: no code path, or the code path is wrong.

## Critical and high gaps (ordered by severity)

No critical item and no privacy finding came out of this pass: the attack paths checked do not log values, tokens or
URLs, the demo store is refused by the sync, import and export paths, and nothing writes to Health Connect or Google.

1. **High, data loss: a corrected clock strands the sync watermark.** If the phone clock runs ahead (manual change,
   bad network time), a sync advances the watermark to that future time (orchestrator:85, :97) and the DAO only
   moves it forward (`SyncWatermarkDao.kt`:35). After the clock is corrected `from = mark - 36 h` is later than
   `end = now` (orchestrator:87, :93), so nothing is pulled until real time catches up, and data from the
   in-between period is never read. Smallest fix: if `mark.lastSyncedEpochMillis > end + 10 min`, read this run
   from `floor` and rewind the stored watermark with a new DAO query (`rewindTo`). Test: sync with a clock +3 days,
   then with the real clock, assert the gap rows arrive. Needs no device.
   **Status: fixed.** `SyncResumePlan.readPlan` treats a watermark more than 10 min ahead of `now` as stale: this run reads from the backfill floor and `SyncWatermarkDao.rewindTo` resets the stored value (a new `@Query`, no schema change). Tests: `dtest/sync/SyncResumePlanTest::aWatermarkFurtherAheadThanTenMinutesIsStaleAndRewoundToTheFloor` (plus 3 siblings), `SyncResilienceRobolectricTest::aClockSetAheadDoesNotStrandTheWatermarkOnceItIsCorrected`, `::aHealthyWatermarkIsNeverRewound`, `database/ApexDatabaseTest::rewindMovesAStaleWatermarkBackAndAReplayMarkSurvivesAdvance`.
2. **High, missing scores after an interrupted run: no owed recompute for sync.** A cancelled or killed sync (or a
   throwing replay) skips `replay` (orchestrator:106, :128-130), the windows it committed stay committed, and the
   next run replays only from its own new data. After an interrupted 90-day backfill the earlier days keep raw data
   but no recovery, sleep or strain scores until the owner runs "recompute". The Takeout engine already solves this
   (`replayPending` and `earliestAffectedEpochDay` in `takeout_file_mark`). Smallest fix: after each committed
   window store `min(pending, earliestAffectedDay)` in a small row (for example on the stream's
   `sync_watermark`), replay from it at the start and end of every run, clear it after a full replay. Test: cancel
   after window 1, run again, assert scores exist for every committed day.
   **Status: fixed.** After each committed window (and in a `finally` for a window that failed or was cancelled midway) the run stores `min(mark, earliestAffectedDay)` as a replay mark on the stream's `sync_watermark` row (`cursorToken`, prefix `replay-from:`; no schema change, see DECISIONS D7). Every run replays from the earliest mark across all rows and clears them only after the replay finished. Tests: `SyncResumePlanTest::theReplayStartIsTheEarliestOfStoredMarksAndThisRun`, `SyncResilienceRobolectricTest::anInterruptedSyncLeavesAMarkAndTheNextRunScoresEveryCommittedDay`, `::aReplayThatThrowsKeepsTheMarkSoTheNextRunTriesAgain`, `::rerunningACompletedSyncChangesNothing`.
3. **High, crash risk on large archives: unbounded per-run heart-rate memory.** `HealthIngestor.Session.writtenMinutes`
   (ingestor:53, :122, :143) holds a boxed `Long` for every minute written in a run, and an archive import is one
   session (`RoomTakeoutSink`, `TakeoutRoomBindings.kt`:27-40). A multi-year archive (a few million minutes) is
   roughly 100 MB or more of heap, estimated, not measured. The 250,000-row bounded-memory test cannot see this
   because it uses a counting sink. Smallest fix: after each heart-rate chunk drop minutes older than the chunk's
   first minute minus one hour (batches and sync windows arrive in time order). Test: ingest 250,000 minutes
   through the real ingestor and assert `writtenMinutes.size` stays below a few thousand; keep the 40 MB-heap
   child-JVM test but point it at a Room-backed or ingestor-backed sink.
   **Status: fixed.** `MinuteLedger` keeps only minutes within one hour of the latest committed chunk, with a hard cap of 10,000 (covers out-of-order input). A split minute re-delivered more than an hour apart is replaced rather than merged (accepted; time-ordered sources never do this). Tests: `MinuteLedgerTest` (5, including 250,000 ascending and descending minutes and a sparse-year adversarial case), `HealthIngestorRobolectricTest::aQuarterMillionHeartRateMinutesKeepTheSessionLedgerBounded` and `::aMinuteSplitAcrossTwoBatchesStillMergesWithTheBoundedLedger`. Still open from this item: the 40 MB-heap child-JVM test still uses a counting sink.
4. **Medium to high, hang and battery: no lower bound on timestamps or daily dates.** `ingestDaily` and
   `ingestSamples` accept any `epochDay` and any positive time (ingestor:168-215); heart rate accepts anything
   after 1970 (ingestor:95). One malformed row dated 1970 or year 1 makes the run replay every day since then
   (`session.touch`, then `replay(earliest, today)` at orchestrator:129 and `TakeoutZipImporter.kt`:109-111),
   which is tens of thousands of analyses. Smallest fix: reject observations before 2010-01-01 (and daily days after
   today + 1, sample times after now + 10 min) in `HealthIngestor`, counted as rejected; tests for each bound.
   **Status: fixed.** `ObservationBounds`: instants before 2010-01-01 or after now + 10 min and daily days before 2010-01-01 or after today + 1 are rejected and counted; sleep and workouts before the floor too. A rejected row never calls `touch`, so it cannot widen the replay. Tests: `ObservationBoundsTest` (4), `HealthIngestorRobolectricTest::heartRateBeforeTheFloorOrAfterTheCeilingIsRejectedAndNeverStored`, `::aBatchOfOnlyAncientHeartRateTouchesNothingAndSchedulesNoReplay`, `::dailyDaysBeforeTheFloorOrAfterTomorrowAreRejected`, `::samplesBeforeTheFloorOrAfterTheCeilingAreRejected`, `::sleepAndWorkoutsBeforeTheFloorAreRejected`.
5. **Medium, stale freshness: no sync when the app opens.** `SyncScheduler`'s KDoc promises it; the code does not do
   it (`syncNow` only from Data Sources and after sign-in). With Doze or an aggressive OEM, data can be a day old
   when the owner looks. Smallest fix: call `SyncScheduler.syncNow` on app start and resume, throttled to once per
   15 minutes, or correct the doc. Device check for the OEM case.
6. **Medium, determinism across travel: day windows follow the current phone zone.** Pipeline:154-157 and :233 cut
   heart-rate days by `ZoneId.systemDefault()`, while sleep and workouts use recorded offsets. After a trip a
   replay gives different past strain, and a travel day's sleep and heart rate disagree. Smallest fix: derive the
   day window from the offset recorded that day (fall back to the last known), with a two-zone replay test.
7. **Medium, short main sleep scored.** A source flag `mainSleep = true` bypasses the 180-minute floor (ingestor:260),
   so a 20-minute main sleep is scored, and the second part of a split night is dropped as a nap. Smallest fix:
   apply the floor to the flag in the ingestor or filter `mainSleepsBetween`; add ingestor sleep tests (there are none).
   **Status: fixed for the flag bypass.** `SleepClassification`: under 180 minutes asleep is never main and is stored as a nap, whatever the source flag says. Split night (unchanged by design): both parts clear the floor, `demoteShorterMainSleeps` keeps the longer as the day's main sleep and demotes the other to a nap, so the second part is not scored (the first part alone is scored; a 4 h + 3 h night is scored as 4 h). A part under 180 min is now a nap even if flagged main, so a split night whose parts are both under 3 h has no main sleep at all and shows NO_SLEEP_DATA. Merging split parts needs a real-archive decision (OPEN_POINTS). Tests: `SleepClassificationTest` (5), `HealthIngestorRobolectricTest::aTwentyMinuteSleepFlaggedMainIsStoredAsANapAndNeverScoredAsMain`, `::aLongSleepFlaggedMainStaysMainAndAShortFlaggedOneOnTheSameDayDoesNotDisplaceIt`, `::splitNightTheSecondPartIsADemotedNapNotAMainSleep`.
8. **Low to medium, lock held across the network.** The orchestrator holds the single write mutex for a whole sync
   including HTTP and replay (orchestrator:62), so a manual save or an import batch can wait for minutes. Smallest
   fix: take the mutex per window (as the Takeout sink does per batch) and for the final replay chunks.
