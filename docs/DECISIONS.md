| D9 | 2026-11-13 | **Release signing and sign-in client type.** (a) The release APK is built by `.github/workflows/release.yml` and signed with a key that is stable across builds, chosen in this order: the four secrets `APEX_KEYSTORE_B64`, `APEX_KEYSTORE_PASSWORD`, `APEX_KEY_ALIAS`, `APEX_KEY_PASSWORD`; else a key **derived from the single secret `APEX_SIGNING_PASSPHRASE`** (`.github/scripts/DeriveKeystore.java`: PBKDF2-HMAC-SHA256, 1,000,000 iterations, public salt `apex-signing-v1` -> HMAC-SHA256 counter stream -> RSA-2048 primes searched by the script itself -> hand-encoded self-signed certificate with fixed serial, validity 2026-01-01 to 2126-01-01 and subject `CN=Apex personal build`, SHA256withRSA PKCS#1 v1.5); else a throwaway key, announced at the top of the job summary. Determinism is proved by `.github/scripts/check-derive-determinism.sh` (separate JVM processes, byte-identical certificate, pinned known-answer test that the workflow re-checks before every passphrase-signed build). No keystore is ever committed. The key is only as strong as the passphrase because the repository is public and the certificate ships in every APK: offline guessing is possible, so the passphrase must be 32+ random characters (the script refuses under 20). (b) The build supports two redirect styles chosen by `apex.oauthClientType` / `APEX_OAUTH_CLIENT_TYPE`: **`ios` (default**; scheme = reversed client ID, `com.googleusercontent.apps.<id>:/oauth2redirect`; the iOS-type client needs no SHA-1) and `android` (the documented fallback; scheme = package name, `com.apex.athlete:/oauth2redirect`, bound to package + SHA-1). The default was first `android` and was flipped to `ios` the same day, on the coordinator's decision, because Google's native-app page says custom URI schemes are not supported for Android-type clients. The manifest placeholder and the runtime `GoogleHealthAuthConfig` must agree; `OAuthSchemeConsistencyTest` and `OAuthClientTypeTest` pin that. The `ios` type is not contradicted by that page but is untested from an Android Custom Tab (`UNVERIFIED-NEEDS-REAL-ACCOUNT`), so `android` stays as the fallback (OPEN_POINTS, "Sign-in client type"). The passphrase secret is still needed before the first kept build so the signature stays stable for updates; it is no longer needed to learn a SHA-1 on the main path. (c) The client ID is compiled into a public Release APK: acceptable because it ships inside every APK and is visible in any OAuth consent URL anyway, there is no client secret (PKCE, public client), and while the consent screen is in Testing only the owner's listed test account can sign in; a leaked ID cannot read anyone's data. | Without stable signing no update could install over an earlier build (data loss) and an Android-type client could never match; the owner has only a phone, so the key must come from something typeable on a phone and the build must run on GitHub. | The consent screen goes In production (anyone could then try the client: revisit quota/abuse and consider restricting), the repository becomes private (a stronger passphrase is then less critical), Google rejects the `ios` style from an Android tab (flip the default back to `android`), or the owner prefers a real keystore (use the four secrets). |
